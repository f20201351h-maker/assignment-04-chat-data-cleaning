1. How many strategies? Nine.

The course material I worked from (ERA V5, Session 4) describes the pipeline in two lists. One has eight stages: extract, normalize, language ID, quality filter, deduplicate, PII scrub, decontaminate, manifest, with ghost tags folded into "normalize". The other also has eight items, but drops extraction and lists format discipline (the ghost-tag trap) on its own. Taking both lists together gives nine. I did not count sub-steps (the nine heuristic rules, exact vs near dedup, regex vs NER, canary strings) as separate strategies, since each belongs to one stage.

  1. 01

    Extraction

    no HTML here

    Turn a raw web page into its text and drop menus, cookie banners and footers. Naive tag stripping keeps that boilerplate as if it were content.

    Both sources already ship plain text inside JSON/Parquet, so there was no HTML to extract. What did apply was the "is the text actually there" part: Anudesh rows had a null or empty prompt/response and were dropped.

  2. 02

    Text normalization

    changed records

    NFC, strip zero-width spaces, BOMs, bidi and control characters, unescape HTML entities, collapse whitespace, but keep ZWJ/ZWNJ where they are part of an Indic word. A byte-level tokenizer learns every stray character (one model in the course case study ended up with 46 garbage tokens), and a cleaner that deletes all invisible characters breaks Indic text.

    Anudesh: kept joiners inside Indic words, removed zero-width spaces, BOMs and stray joiners; NFC rewrote fields. Glaive: almost only whitespace, plus control characters.

  3. 03

    Format discipline (the ghost-tag trap)

    changed records

    Pick one conversation format with real special tokens and rewrite every source into it. Literal markers like USER: get learned as ordinary text and later fight the real special tokens during SFT.

    Converted literal markers in Glaive into roles (including literal <|endoftext|> strings), which saved tokens. Repaired function calls that were not valid JSON. Dropped corrupt rows.

  4. 04

    Language ID and validation

    removed records

    Detect each document's language at runtime and check it against what the source claims, instead of trusting a folder name or label. Mislabels skew every per-language number.

    Removed conversations whose user text or reply was confidently in a language outside the corpus targets. Flagged (but kept) replies in a different Indic language from the question, and kept code-switched conversations as "mixed".

  5. 05

    Quality filtering

    removed records

    Cheap heuristic rules first (Gopher/C4 style), then a classifier trained on labels from a bigger model. Junk wastes compute, but rules tuned on English throw away good Indic text.

    My chat-specific rules removed conversations (greeting-only prompts, replies stuck in a loop, LaTeX broken upstream). Run as written, the standard heuristic rules would have dropped of Indic answers, so I only used them as an audit. The classifier layer is in section 4.

  6. 06

    Deduplication

    removed records

    Exact hashes, then near duplicates with shingles, MinHash and LSH, across the whole corpus rather than shard by shard. Repeats waste compute and push the model to memorise.

    Removed exact and near duplicates, almost all from Glaive, whose generator repeated the same scenarios (one pizza refusal appears times). Duplicates across the two sources: .

  7. 07

    PII removal

    changed records

    Regex for structured identifiers (emails, phone numbers, IP addresses) and a name layer for people. The name layer is where precision and recall fight, especially for Indic names and places.

    Masked emails, phone numbers and public IPs. Kept example.com-style addresses and private/loopback IPs. Names were audited on a sample, not masked (section 4 says why).

  8. 08

    Decontamination

    removed records

    Fingerprint the evaluation sets, scan the training data for overlap, remove hits. Otherwise a benchmark score measures memory, not ability.

    Scanned against test items from GSM8K, MATH-500, HumanEval and MMLU. conversations shared a 13-word sequence with a test item. I read all of them: none is a copied test question.

  9. 09

    Reproducibility and the manifest

    checked

    Same input and config must give the same output, IDs come from content, and every shard carries a manifest (source, licence, contributor, script hashes, content hash, tokens, languages). No manifest, no ingest.

    Two shard manifests, both admitted. A full second run produced identical content hashes: .

2. The dataset I picked

The target was a 10 to 100M-token chat dataset of the kind people generate with a model and put on Hugging Face. I looked at about 20 candidates (reasoning distills, real chat logs, function-calling sets, Indic instruction sets) and measured the two I picked myself.

Why these two:

  • They match an SFT mix I had planned. The plan was a model that is good at agentic work and Indian languages, with a 30% Indic share in SFT. Glaive covers tool calling, and IndicAlign comes from IndicLLMSuite (AI4Bharat). This is a small pilot of that mix.
  • It is the classic ghost-tag situation. Glaive writes speakers as literal text (USER:, ASSISTANT:, <|endoftext|>), Anudesh stores [prompt, response] lists. Two sources, two formats, one canonical format needed.
  • The problems are real and different. Glaive breaks on format and duplication, Anudesh on script and language. Neither card mentions deduplication or PII scrubbing, and the data confirmed it. I did not pick them for big removal numbers.

No sampling was needed: each source is inside 10 to 100M tokens on its own and the two together are still under 100M. From IndicAlign (28 GB in total) I took only the Anudesh file. Both are pinned to a commit and checked by sha256.

Licence note that goes in the manifest: Anudesh's answers were generated by Llama-2-70B-Chat, and the Llama 2 licence restricts using its outputs to improve other models. Glaive's card does not say which model generated it. I am not republishing the cleaned files.

4. What I cleaned, why, and how

Normalization: keep the joiners, drop the junk

A minimal normalizer is about fifteen lines. Mine does the same steps but is longer because it has to know about code and scripts: NFC, remove ZWSP / BOM / bidi controls / C0-C1 controls / soft hyphens / private-use / U+FFFD, unescape real HTML entities, collapse whitespace. Two decisions of my own: whitespace inside code blocks is left alone (Python indentation is meaningful), and a ZWJ or ZWNJ is kept only when it sits next to a Brahmic or Arabic-script letter or inside an emoji sequence.

A ZWNJ kept inside a word (shown as a green chip):

A zero-width space removed (red chip before, gone after):

NFC changed Anudesh fields. These were almost all Bengali য় and Devanagari letters like ज़ stored as one precomposed code point; NFC splits them into letter + nukta, so the two spellings of the same letter now tokenize the same way. The stray joiners I removed were inside Latin words, in runs of three between spaces, or left over from emoji whose base character was lost. On Glaive, normalization was almost all whitespace: only conversations had a real encoding fix.

Format discipline: one format with real special tokens

Glaive stores each conversation as one string with role markers typed into the text, and it is not even consistent with itself: function-calling rows separate turns with three newlines, plain-chat rows with two. I parse the markers into roles and store conversations as {role, content, tool_call} messages. When the data is turned into training text, each turn starts with one special token (<|system|>, <|user|>, <|assistant|>, <|tool|>) and the conversation ends with a single <|end|>.

of Glaive's function calls were not valid JSON, because the arguments were written as a single-quoted string ("arguments": '{"country": "France"}'). I decode that string back into a JSON object; for of them I also had to undo escaped apostrophes (It\'s). A model trained on the original would learn to emit broken tool calls.

I also trimmed conversations that ended on a user message with no answer (nothing to learn from that last turn).

Language ID: target languages only

Each conversation gets two detections, one for the user turns and one for the replies: a script histogram, then py3langid for Latin-script text, plus a small word list for Hindi typed in Latin letters, which no off-the-shelf detector has a label for. A detection only counts at confidence or more. Language codes go through a strict table that raises on anything unknown, so a te/tel mix-up fails loudly in a test.

The removals are conversations confidently in a language outside the corpus targets (English plus the 14 Indian languages IndicAlign lists). Most were the model answering in the wrong language. In Anudesh, Llama answered a Telugu question written in Latin letters in Spanish, a one-word prompt in French and an Urdu-script request in Persian; in Glaive, an English request for SQL got its answer in French.

I first also dropped replies written in a different Indian language from the question. Reading what that caught changed my mind: "list out all the alphabets in Telugu" and "teach me ten Telugu words using Kannada and Hindi" are good conversations where the answer should switch language. That rule now only flags ( conversations).

Quality filtering: two layers, and an English bias

I ran the nine standard heuristic rules (Gopher/C4 style) as written on every assistant reply, with code blocks removed. On this data they are not usable as a filter. The chart shows how often each rule fails on Anudesh replies, split by the script of the answer (same prompts, same model; only the script differs):

Table view

The "at least two of the, be, to, of, and, that, have, with" rule fails of Indic answers by construction, and the 50-word minimum fails every short correct answer. Overall the rules would drop of Indic answers but of Latin-script answers from the same dataset. English-tuned rules throw away correct Telugu, Hindi and Bengali text at scale. So I kept the audit numbers and used rules that make sense for chat in any script:

  • the only user message is a bare greeting ("hi", "Hello", "नमस्ते");
  • an assistant reply that is empty;
  • a reply stuck in a loop: a short piece of text repeated or more times in a row (,000,000,000…, quad quad quad…), with code blocks, table rows and rule lines ignored;
  • a reply whose LaTeX has visibly lost its backslashes (see section 5).

The loop rule is my second version. The first used the heuristic set's own repetition thresholds (one character pair at 20% or more of the text, 30% or more repeated lines), since those do not depend on language. A review of of those removals found were fine: markdown tables, a guitar tab, a binary-encoded answer the user asked for, meal plans and seating charts where items repeat on purpose. So I replaced both with a rule that looks for the loop itself.

Layer 2, the classifier. I used the usual recipe at toy scale: an LLM (Claude Sonnet, following a written rubric) scored random cleaned conversations from 0 to 5 for how useful they are as SFT data, and I trained a small logistic-regression model on hashed character n-grams to imitate those scores. On held-out conversations it gets an AUC of , which sounds fine until you split by script. The labels keep of the held-out Indic conversations; the classifier keeps . It learned "Indic script means low quality".

Part of that is real. The labeller itself kept only of Indic conversations against of the others, mostly because Llama-2 often answers questions in Indian languages with a bare "I don't know" or with garbled text. But the classifier turns a quality gap into a script filter. A model trained only on Indic labels ranks them much better (AUC ), but from examples, which is too few to delete data with. So the classifier removes nothing here, and its scores are kept as an audit. This is the familiar problem of an English-heavy quality proxy undervaluing Indic data, small enough to see in one table.

Deduplication: exact, then MinHash + LSH, globally

Exact duplicates are found by hashing the whole cleaned conversation. For near duplicates I implemented the three standard steps myself: word 5-gram shingles, MinHash signatures with hashes, and LSH with bands of rows (the FineWeb setting; the S-curve midpoint is (1/b)1/r = ). LSH only proposes candidates. Every candidate pair is then checked with its true Jaccard, and only pairs at or above count.

The dedup ran over both shards together (global, not per shard), but it found near duplicates and exact duplicates across the two sources. That makes sense, since an English tool-calling set and an Indic prompt set do not share text. Global and local dedup gave the same answer here, and the global pass would only start to matter with overlapping sources (for example two web crawls).

PII: mask structured identifiers, audit names

The regex layer covers emails, phones and IPs (with typed placeholders [EMAIL] [PHONE] [IP]), with a few changes to cut false positives on this data. A phone number needs a phone shape (country code, area code or separator groups); a bare 10-digit number in a maths answer is left alone. Only globally routable IPs are masked: 127.0.0.1 and 192.168.x.x are not personal. An IPv6 match needs at least three groups, because the review below caught Python slices like a[0::2] and flashcard markers like {{c1::...}} being masked as addresses. Only the reserved example domains (example.com, .test) count as placeholders, because domains like mail.com are real.

For names I did not run a model over the whole corpus. I had an LLM mark every person name in random cleaned conversations. were public figures (politicians, cricketers, authors, scientists, deities), were fictional or placeholder names, and looked like private people. Another words would probably have been caught wrongly by a name detector: brands, temples, festivals, and Indic common nouns that are also given names (tulsi, ganga). Most of the public names in Anudesh are written in Indic scripts, where a capitalisation-based detector sees nothing. Masking names here would remove public facts and protect nobody (masking "Mahatma Gandhi" helps no one), so names were left in.

Decontamination: the scan found phrases, not leaks

I fingerprinted the test splits of the openly downloadable evaluation benchmarks (GSM8K, MATH-500, HumanEval, MMLU; MILU is gated), distinct 13-word sequences in all, and scanned every conversation. conversations matched at least one. I read every hit. None is a copied test question. They share the opening of A Tale of Two Cities or a line of the Declaration of Independence with MMLU history questions, the textbook phrase "where B is the area of the base and h is the height", a generic statistics phrase, or a nested for loop. I removed them anyway, since the rule is meant to be conservative and it costs nothing, but "no contamination" here only means: no overlap with these four test sets at the 13-gram level. Manifest and reproducibility

Each shard has a manifest with the standard provenance fields plus a few more: source URL and commit, file sha256, licence and a terms note, contributor, every cleaning script by name and code hash, the config hash, the sha256 of the cleaned file, token count, and language shares. A shard is blocked if the licence is unknown or a required field is missing. Document IDs are the sha256 of the cleaned conversation, and the shard ID comes from the content hash. No timestamp is part of any ID.

7. What surprised me

  
I expected normalization and PII to be the busy stages. On this data, deduplication did most of the
  removing: Glaive's generator kept producing the same few scenarios, and one refusal appears
   times with only the last clause changed. On the other hand, the most damaging defect
  in Glaive did not remove anything at all. It was the tool-call JSON, broken in 
  of function calls, which no filter would catch because the text looks fine.

  
The other surprise was how strong the English bias of the heuristic rules was. I ran the heuristic rules expecting to tune
  them a bit; instead they marked almost every Telugu, Hindi and Bengali answer as junk because those answers do not contain
  "the" or "and". If I had used them as the filter, the Indic half of this corpus would have disappeared while the English half
  looked fine. And the decontamination scan's 13-gram hits looked like contamination until I read them.
